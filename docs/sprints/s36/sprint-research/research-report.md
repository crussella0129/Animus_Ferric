## 1. Sprint Goal
Answer the "ADR-005 security call" that has blocked `ferric mcp` since sprint 1, then build the MCP-stdio server it unblocks. Concretely: decide what surface an external MCP client (Claude Code, Cursor, an IDE) can actually invoke through Ferric, prove that surface inherits every containment/permission guarantee `ferric query` already has (no new privilege, no bypass of the guard/workspace boundary), and ship a minimal `ferric mcp` subcommand implementing it. The companion decision (drop the mistral.rs in-process hang investigation — HTTP valve remains the only backend that matters) was made in conversation, not delegated to this report; it needs no further research and is not part of this sprint's build.

## 3. External Sources
- [Transports — Model Context Protocol spec (2025-11-25)](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) — confirms stdio transport is newline-delimited JSON-RPC 2.0 over stdin/stdout; server writes logs to stderr, never stdout (stdout is reserved for protocol messages — a hard constraint on any implementation, hand-rolled or not).
- [modelcontextprotocol/rust-sdk (`rmcp`) on GitHub](https://github.com/modelcontextprotocol/rust-sdk) — the official Rust MCP SDK; tokio-based, `rmcp = { version = "0.16", features = ["server"] }`, `service.serve(stdio()).await`. Confirms a viable off-the-shelf path exists if full MCP-spec compliance (resources, prompts, capability negotiation, notifications) is wanted.
- [How to Build a stdio MCP Server in Rust — Shuttle blog](https://www.shuttle.dev/blog/2025/07/18/how-to-build-a-stdio-mcp-server-in-rust) — corroborates the minimal handshake shape (`initialize` → `tools/list` → `tools/call`) and the "never `println!()`, all logging to stderr" constraint that would corrupt the protocol stream otherwise.

## 4. Risks, Unknowns, Dependencies
- **Risk — workspace root as a per-call parameter would be a containment hole.** If the MCP tool schema let a caller pass an arbitrary `workspace` path per `tools/call`, a compromised/confused client could redirect Ferric's containment root anywhere the OS-level process can reach, then operate freely under that new root — the boundary logic (`Workspace::resolve`) would still be enforced, but enforced against a root the human operator never chose. **Mitigation (recommended, see §5):** the workspace root is a `ferric mcp` *launch-time* CLI argument (default: CWD, exactly like `ferric query`'s default), fixed for the life of the server process. The per-call MCP tool schema does not expose a `workspace` field at all.
- **Risk — exposing individual builtin tools (read_file/write_file/exec) over MCP instead of the whole-task `query` capability.** This would let an external MCP client bypass Ferric's own agentic loop (planning, ring limits, no-progress/repetition/failure guards, per-turn tracing) and use Ferric as a bare filesystem/exec proxy — defeating ADR-001's "harness owns decoding" thesis and turning Ferric into something closer to an unrestricted MCP filesystem server. **Mitigation (recommended, see §5):** expose exactly one MCP tool, equivalent to `ferric query` (a task prompt in, a final answer + trace path out); the constrained loop, its guards, and its tracing run underneath exactly as they do today. This is also what ADR-012's "same surface serves Claude Code/Codex/Cursor" line implies — one capability, not a tool-by-tool passthrough.
- **Risk — model/backend selection as a per-call parameter.** Letting an MCP client request an arbitrary backend/model per call re-opens a resource-exhaustion / config-injection surface (spin up arbitrary GGUF loads on demand) and violates "hardcoded, harness-owned" (ADR-005). **Mitigation:** backend/model config, like the workspace root, is fixed at `ferric mcp` launch time via the same `BackendOpts` flags `ferric query` already takes.
- **Unknown — `rmcp`'s real dependency weight.** The web fetch to inspect its transitive Cargo tree failed; only the top-line `features=["server"]`/tokio-based nature is confirmed from the GitHub README, not the full graph. Not blocking (see recommendation), but worth a `cargo tree` check in the Plan phase if `rmcp` is chosen.
- **Unknown — concurrent `tools/call` requests.** Whether a real MCP client (Claude Code, Cursor) ever pipelines multiple concurrent tool calls in one session, versus always awaiting one before sending the next. Recommendation below scopes sprint 36 to serialized (one call processed at a time) regardless, which is correct either way and avoids a concurrent-workspace-mutation hazard; revisit only if a real client is observed pipelining.
- **Dependency — this sprint does not touch the raw chat mode.** The ADR-011 revision's second half stays deferred to its own future sprint with its own ADR, per the existing agent-tasks.md note. No design decision here should implicitly prejudge that ADR.
- **Dependency — streaming.** `Provider::complete()` is single-shot; an MCP tool call today returns only after the full constrained loop finishes (same latency profile as `ferric query`). This is an accepted, known gap (tracked separately from the GLM review), not something this sprint fixes.

## 5. Recommended Approach
**Primary:** Hand-roll a minimal MCP-stdio server inside `ferric-cli` (new `mcp.rs`, wired as `Command::Mcp` in `main.rs`), exposing **exactly one MCP tool** — `ferric_query` — whose input schema is `{ prompt: string, files?: string[] }` (mirroring `QueryArgs::prompt`/`files`, minus everything else). Workspace root, backend/model config, and protocol are **launch-time CLI flags** on `ferric mcp` (reusing `BackendOpts` and the workspace-default logic already in `query.rs`), never per-call parameters. Each `tools/call` constructs one `RunArgs` and calls `run()` exactly as `drive_real`/`drive_mock` do today, writing its own JSONL trace with the same `q-{ms}` session convention. The handshake is the minimal MCP lifecycle: `initialize` (capability negotiation, declare one tool), `tools/list` (return the `ferric_query` schema), `tools/call` (drive one loop, return `final_text`). All logging goes to stderr; stdout is reserved for JSON-RPC frames (per the spec source above). Calls are processed serially off a blocking read loop — no new concurrency model needed, matching `ferric query`'s single-shot nature.

**Alternative considered:** depend on `rmcp` (`modelcontextprotocol/rust-sdk`), the official SDK, and implement `ferric_query` as an `#[tool]`-macro-annotated service. This buys full MCP-spec correctness (proper capability negotiation edge cases, future resources/prompts support, maintained-upstream protocol compliance) at the cost of a new tokio-based dependency whose exact transitive footprint wasn't verifiable this session (see Unknown above), and needs the same `Cargo.toml`-comment justification every prior dependency got.

**Rationale:** The MCP surface this sprint needs is deliberately narrow — one tool, no resources, no prompts, no sampling callbacks, no notifications. Hand-rolling that narrow slice is a few hundred lines of `serde_json` message handling reusing infrastructure (`tokio`, already a feature-gated workspace dep for backend-openai/backend-mistralrs) Ferric already has, with zero new external protocol-implementation dependency and full auditability (ADR-013's ownership-graph goal). It also makes the "ADR-005 security call" easier to state and verify precisely: the tool schema *itself* has no `workspace`/`backend`/`model` fields, so the containment guarantee is structural (unrepresentable in the wire protocol) rather than something a handler must remember to enforce. If a future sprint needs the fuller MCP surface (resources, prompts, multi-tool exposure for the eventual Development Engine), revisit `rmcp` then with an actual dependency-tree measurement — deferring that decision costs nothing now.
