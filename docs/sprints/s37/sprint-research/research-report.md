# Sprint 37 Research Report

## Decisions Reviewed
- **2026-06-10 ADR-003 — Provider trait is async, dyn-compatible, constraint-carrying** (sprint 0) — relevance: this is the ADR that explicitly reserved streaming as a future extension point ("`complete_stream` yielding `ProviderEvent`s") but never built it. Confirmed by grep: `ProviderEvent`/`complete_stream`/`StreamSink` do not exist anywhere in the codebase today — this sprint is genuinely from-scratch design, not filling in a stub.
- **2026-06-10 ADR-004 — CPU-first portability, s0 dependency allowlist, aarch64 CI gate** (sprint 0, amended by ADR-016/045) — relevance (added post-plan-critique, C-010): this is the ADR that actually governs whether the `reqwest`/`tokio` feature additions T-3703 needs are in-policy. Both are pure feature-flag additions on already-approved crates (no new crate), and the `tokio` `net` feature is scoped test-only (T-3703's fake-server E2E), not a production dependency growth — in the same spirit as ADR-016's/ADR-045's prior allowlist-amendment precedent. The default aarch64/no-tokio build is unaffected (`reqwest`/`tokio` remain `backend-openai`-feature-gated).
- **2026-06-11 ADR-010 — Constraint and native tool calling are mutually exclusive per request** (sprint 1) — relevance: streaming must not touch this invariant. A streamed request still carries either `Constraint` or `tools`, never both; only the *consumption* of the response becomes incremental.
- **2026-06-13 ADR-015 — Unified action grammar via ActionProtocol** (sprint 2, amended by ADR-022) — relevance: the field-ordering discipline this ADR established (`tool` serialized before `args`, `const` discriminator first) is exactly what makes a cheap "which tool is being called" streaming signal possible before the full JSON object is available — a reuse of an existing decision for a new purpose, not a new one.
- **2026-06-23 ADR-022 — Constraint reinstated, ADR-010 re-enforced, capabilities honest, action-protocol trichotomy** (sprint 7) — relevance: `ConstrainedJson` is the thesis path (server-enforced `response_format`). Streaming must preserve "the harness owns decoding" — the constraint enforcement and the dispatch logic must be byte-for-byte unchanged; only the *display* layer becomes incremental.
- **2026-06-23 ADR-023 — the HTTP valve is the workhorse; functionality outranks Rust purity** (sprint 7→8) — relevance: streaming should target the OpenAI-compatible HTTP backend (the workhorse) first; mistral.rs (the fallback, `TextXml`-only, ADR-020/027's hang) is not this sprint's concern.
- **2026-06-29 ADR-045 — expert review + refactor** (sprint 35) — relevance: streaming was explicitly deferred there as a real product gap, "its own focused increment" — this sprint is that increment.
- **2026-07-03 ADR-046 — `ferric mcp`** (sprint 36) — relevance: `ferric mcp`'s stdout is reserved EXCLUSIVELY for JSON-RPC frames (ADR-046). Streaming partial completion text to an MCP client requires MCP's own notification mechanism, which is a distinct, larger feature. This sprint scopes streaming to `ferric query`'s CLI experience only; MCP streaming is called out as a deferred follow-on, not silently ignored.

No prior decision is being violated: this sprint adds a genuinely new capability (per ADR-003's own reserved slot) without altering ADR-010's mutual-exclusion invariant or ADR-022's constrained-decoding guarantee.

## 1. Sprint Goal
Design and build streaming inference as a **base architectural choice** (the user's framing) — the foundational piece other future work builds on, not necessarily the full "everything streams beautifully" experience in one sprint. Concretely: extend the `Provider` trait with a real streaming capability, implement it for the OpenAI-compatible HTTP backend (llama-server/Ollama), and reconcile it with the constrained-decoding thesis so a user watching `ferric query` run sees live text instead of a wall of silence — without weakening the guarantee that "the harness owns decoding."

## 4. Risks, Unknowns, Dependencies
- **Risk — streaming intermediate `ConstrainedJson` turns has no useful "text" to show.** For tool-calling turns (not the final answer), the ENTIRE completion is one opaque `{"tool":...,"args":...}` JSON blob — raw token deltas of this are not human-readable prose. Naively echoing raw JSON tokens to the user would be worse UX than silence. **Mitigation:** distinguish two streaming behaviors: (a) a cheap **activity signal** — as soon as the early-committed `"tool":"<name>"` field is decodable (ADR-016's ordering), surface "▸ calling `<name>`..." — no incremental JSON parsing of `args` needed, just watching for one substring; (b) genuine **live text** only for the field that IS human-readable prose: `task_complete`'s `args.summary` string value (the final answer), which requires a small incremental-string-extraction scanner (recognize entering the `"summary":"` value, decode escaped characters as they arrive, stop at the unescaped closing quote). `NativeTools`/`TextXml` protocols don't have this problem — their `content` field (when present) is already plain prose, streamable via `delta.content` with no extraction needed.
- **Risk — reconciling streaming with the constrained-decoding guarantee.** The constraint (`response_format`/`json_schema`) is enforced **server-side** by llama-server/Ollama regardless of streaming; streaming only changes how the client receives an already-being-enforced response, not what's enforced. The full JSON object is still validated/parsed by Ferric's existing dispatch logic exactly as today, AFTER the stream completes — nothing about "the harness owns decoding" changes. This is the "buffer-and-validate" approach the reviewed production-readiness plan doc names, and it holds up under inspection: buffering is for *display*, not for *validation*, which stays synchronous and unchanged.
- **Risk — retry/backoff semantics under a partially-received stream.** `complete_with_backoff` currently retries a whole `complete()` call on a retryable error. A stream that fails PARTWAY through (some tokens already displayed) can't be transparently retried the same way — the user would see duplicate or inconsistent partial text. **Mitigation, deliberately simple for this increment:** do not retry mid-stream; a stream error becomes a `ProviderError::RetryableBackend`/`Backend` exactly as today, discarding any partial display state and reporting the error at the turn level — the SAME behavior as today's non-streaming failure path, just discarding a partially-printed line first. Making mid-stream retry seamless (e.g., re-emitting the same partial text without duplication) is real design work better left to a follow-on once basic streaming is proven.
- **Unknown — how much of the loop-internal turn processing should be "stream-aware."** The turn loop (`run.rs`) fundamentally needs the FULL parsed `Completion` before it can dispatch a tool call or terminate — this does not change. The open design question is narrower: does the loop pass a "display sink" callback down to the provider (so the provider can push tokens to it as they arrive, while still returning the same `Completion` at the end), or does streaming live entirely inside a NEW provider method that the CLI opts into, bypassing the loop's normal `run()` for streaming runs? The former (a sink threaded through `RunArgs`) is more architecturally consistent (same code path, streaming becomes an additive concern) and is the recommended approach below.
- **Dependency — `reqwest`'s `stream` feature.** Currently absent from the workspace's `default-features = false, features = ["json", "rustls-tls"]` reqwest config (sprint 35, ADR-045). Needed to call `.bytes_stream()` on a `Response`. Small, well-understood addition — no new crate, just a cargo feature flag; does not affect the aarch64/no-tokio default build since `reqwest` itself is already `backend-openai`-feature-gated.
- **Dependency — MCP-side streaming is explicitly NOT this sprint.** `ferric mcp`'s stdout purity constraint (ADR-046) means partial-text notifications to an MCP client need MCP's own notification/progress mechanism — a distinct, larger follow-on, not silently dropped but explicitly out of scope here.
- **Dependency — mistral.rs backend streaming is explicitly NOT this sprint.** It's the fallback path (ADR-023), `TextXml`-only, and its own constrained-decoding hang is a known, deliberately-not-re-chased issue (ADR-020/027, reaffirmed sprint 36). Streaming there would be a separate, smaller follow-on if ever prioritized.

## 5. Recommended Approach
**Primary:** Extend the `Provider` trait with a new method reusing the existing `Completion` return shape rather than introducing a new `Stream`/`futures` dependency: `async fn complete_streaming(&self, request: CompletionRequest, on_delta: &dyn Fn(&StreamDelta)) -> Result<Completion, ProviderError>`, where `StreamDelta` is a small enum (`Text(String)` for prose deltas, `ToolNamed(String)` for the early-committed tool-name signal). The DEFAULT trait implementation calls the existing `complete()` and fires a single `StreamDelta::Text` (or nothing, for pure tool-calling completions) once the whole result is in — so every existing provider (mock, mistral.rs) works unchanged with zero code, and only `OpenAiProvider` overrides it with a real implementation. This callback shape avoids pulling in `futures`/`tokio-stream` (ADR-004's minimal-dependency discipline) and keeps the function's return type identical to `complete()` — the loop still gets one `Completion` at the end, unchanged.

For `OpenAiProvider::complete_streaming`: set `"stream": true` in the request body, call `.send()`, then read `.bytes_stream()` (needs `reqwest`'s `stream` feature) line-by-line, splitting on the SSE `data: ` prefix and blank-line delimiters, parsing each JSON chunk, accumulating `delta.content` into the final message text and `delta.tool_calls` into the final tool-call list (by index — Ferric only ever sees one tool call per turn in practice, so the documented Ollama multi-call indexing bug is a non-issue), while ALSO invoking `on_delta` per chunk: for `ConstrainedJson`, run the accumulated text through a small incremental scanner that recognizes the `"tool":"..."` prefix (fire `ToolNamed` once) and, once inside `"args":{"summary":"`, live-decodes and fires `Text` for the summary's characters as they arrive; for `NativeTools`/`TextXml`, `delta.content` IS already prose — fire `Text` directly, no scanning needed. At stream end, parse the fully-accumulated text as the existing non-streaming path already does, producing the identical `Completion` — dispatch/validation logic in `ferric-loop` is untouched.

Wire ONE new field into `RunArgs`: an optional display sink (`Option<&dyn Fn(&StreamDelta)>`), threaded down to a new `run_with_provider`-level call to `complete_streaming` instead of `complete_with_backoff` when present. `ferric query` gains `--stream` (opt-in this increment, not default-on — a conservative first step); when set, it passes a sink that prints deltas to stdout live (flushing per delta) and swallows `ToolNamed` as a `stderr` activity line ("▸ calling write_file..."), leaving the final `println!(outcome.final_text)` unchanged as a fallback/complete-answer echo for any turn that wasn't streamed (e.g., `--mock`, or a provider using the default trait impl).

Explicitly out of scope this sprint (follow-ons): MCP-side streaming (needs MCP's notification mechanism, ADR-046's stdout-purity constraint); mistral.rs backend streaming (fallback path, not prioritized); mid-stream retry (a stream error simply reports as today's non-streaming error, discarding partial display); a "structured JSON streaming mode for programmatic consumers" (the plan doc's second flag idea — worth its own increment once raw human-readable streaming is proven).

**Alternative considered:** implement `Provider::complete_stream` returning a real `impl Stream<Item = Result<StreamEvent, ProviderError>>` (the ADR-003 doc-comment's original phrasing), consumed via `futures::StreamExt` combinators in the loop. This is the more "idiomatic async Rust" shape and would generalize better if Ferric ever needs true concurrent/cancellable streams. Rejected for this increment: it requires a new `futures-util`/`tokio-stream` dependency (`futures-executor` alone doesn't provide `Stream` combinators), adds a lifetime/pinning complexity cost to a dyn-compatible trait (`Provider` must stay object-safe per ADR-003 itself — an `impl Stream` return type is NOT object-safe without boxing, which reintroduces most of the callback approach's simplicity cost anyway), and buys little for THIS sprint's actual goal (get live text to the CLI user) versus the callback shape. Revisit if a future sprint needs stream cancellation, backpressure, or multiplexing multiple concurrent streams — none of which apply to Ferric's one-turn-at-a-time loop today.

**Rationale:** The callback shape is the smallest change that (a) fills ADR-003's reserved extension point, (b) preserves `Provider`'s dyn-compatibility with zero new trait-object complexity, (c) gives every non-OpenAI provider a free, correct default (no streaming, but still compiles and behaves identically to today), and (d) cleanly separates "the harness owns decoding" (unchanged: the full `Completion` is still parsed/validated/dispatched exactly as before) from "the user sees text as it's generated" (a purely additive display concern). The `ConstrainedJson` summary-field-extraction piece is genuinely novel work and the sprint's most interesting problem — sizing it as a small, isolated, thoroughly-unit-tested pure function (given text-so-far, return what's newly displayable) keeps it testable without a live model or even a real HTTP stream.
