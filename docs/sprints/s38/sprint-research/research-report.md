# Sprint 38 Research Report

## Decisions Reviewed
- **2026-06-10 ADR-005 — Security is hardcoded and harness-owned** (sprint 0) — relevance: a config file is a NEW input surface the LLM never sees or controls (it's read by the harness at launch, same trust tier as CLI flags) — it must not become a channel for a user-supplied config to weaken guard/denylist behavior. This sprint's config covers model/backend/tuning defaults only, never security policy.
- **2026-06-10 ADR-006 — The scale function is pure, deterministic, config-fed** (sprint 0) — relevance: `ModelProfile` fields (`params_b`, `quant`, `ctx`, `family`) are explicitly "config-supplied, never inferred from filenames" — this is exactly the kind of value a project config file should be able to default, since it's already a config-shaped input, not a new category of thing being introduced.
- **2026-06-11 ADR-013 — Ownership-graph boundaries are named, not absolute** (sprint 1) — relevance: adding a cross-platform user-config-directory resolver is a candidate for either a small new dependency (`dirs`/`directories`) or a hand-rolled `std::env`-only function — a real, small ADR-004-style choice this sprint has to make.
- **2026-06-13 ADR-016 — oovra dependency + s2 allowlist growth** (sprint 2) — relevance: `ferric-prompt`'s existing system-prompt composition (`compose_system_prompt`) is the established mechanism for assembling prompt text from parts. `Animus.md` is a DIFFERENT kind of input (freeform, user-authored, unversioned prose, analogous to `CLAUDE.md`) — not another oovra element — so it should NOT be forced into the oovra recipe system; it composes alongside it as a distinct, simpler mechanism.
- **2026-06-23 ADR-023 — the HTTP valve is the workhorse; functionality outranks Rust purity** (sprint 7→8) — relevance: `BackendOpts`' fields (`model`, `api_base`, etc.) are exactly the values a user re-types on every invocation against a fixed local model/server — the highest-value config target.
- **2026-06-27 ADR-035 — Gemma 4 E4B is the reference model** (sprint 25) — relevance: a project's `config.toml` is the natural place to pin "this workspace always uses Gemma 4 E4B via the OpenAI valve," removing the need to repeat `--backend openai --model gemma4:e4b` on every `ferric query`.
- **2026-07-03 ADR-046 — `ferric mcp`** (sprint 36) — relevance: `ferric mcp`'s `McpArgs` mirrors `QueryArgs` minus `prompt`/`files` and is ALSO launch-time-fixed CLI-flag-driven — the same config-defaulting mechanism should apply to both surfaces, not just `ferric query`.
- **2026-07-03 ADR-047 — streaming inference** (sprint 37) — relevance: `--stream` is exactly the kind of "flag a user wants on by default for their workflow" that a config file should be able to default too.

No prior decision is being violated: this sprint adds a new, harness-owned, non-security config input (ADR-005's boundary preserved) and a new, separate freeform-prose mechanism alongside (not inside) the existing oovra prompt-composition system (ADR-016 unchanged).

## 1. Sprint Goal
Two related, user-requested pieces: (1) **persistent configuration** — a layered `.ferric/config.toml` (project) + a user-level config file, so `ferric query`/`ferric mcp` don't need the same backend/model/tuning flags re-typed on every invocation (CLI flag still always wins); (2) **`Animus.md`** — a project-root, freeform, user-authored instructions file (the user's own framing: "much like CLAUDE.md but for Animus") that gets folded into the system prompt as project-specific context, distinct from and alongside the existing oovra-composed prompt.

## 4. Risks, Unknowns, Dependencies
- **Risk — clap's `default_value_t`/`default_value` fields can't distinguish "user explicitly passed this" from "clap's baked-in default."** `params_b`, `quant`, `family`, `ctx`, `temperature`, `profile_dir`, and `BackendOpts::backend` all currently have hardcoded clap defaults, so today `args.temperature` is ALWAYS a concrete `f32` — there is no way, downstream, to tell whether the user typed `--temperature 0.0` or simply didn't pass the flag. To let a config file supply one of these values as a real default (correctly overridden by an explicit CLI flag), the affected fields need their clap `default_value_t`/`default_value` REMOVED (becoming bare `Option<T>`), with the actual default applied manually AFTER merging in config: `cli_value.or(config_value).unwrap_or(built_in_default)`. This is a real, if mechanical, field-type change rippling into `run_query`/`build_run_config`'s existing references to these fields — sizeable enough to warrant its own task, not a drive-by.
- **Risk — a config file becoming a de facto second security-policy input.** ADR-005 requires security to stay hardcoded/harness-owned. This sprint's config MUST be scoped to model/backend/tuning/workspace-preference values only — never anything touching the guard/denylist/permission system. Explicitly bounding the `Config` struct's fields (rather than a free-form untyped map) makes this a structural guarantee, not a code-review hope.
- **Risk — `Animus.md` becoming a prompt-injection vector.** Unlike Ornstein's quarantined web/tailnet-plane content (untrusted, no-tools model summarization), `Animus.md` is a file the WORKSPACE OWNER authored themselves (same trust tier as the codebase they're already asking the agent to operate on) — it is not untrusted external content requiring quarantine. It should be treated the same as the existing hardcoded `DEFAULT_SYSTEM_PROMPT`/oovra-composed prompt: trusted harness-level context, not routed through Ornstein. Worth stating explicitly in the ADR so a future sprint doesn't conflate "a file on disk" with "untrusted content" and misapply quarantine machinery where it isn't needed.
- **Unknown — cross-platform user-config-directory resolution.** No `dirs`/`directories` crate exists in the tree today. Options: (a) hand-roll ~15 lines using `std::env::var("XDG_CONFIG_HOME"/"HOME")` (Linux/macOS) and `"APPDATA"` (Windows) — zero new dependency, matches the project's demonstrated preference for small hand-rolled utilities over a crate for a narrow need (e.g. the hand-rolled base64 encoder, ADR-004's minimal-dependency spirit); (b) add a small, well-known crate (`dirs` is tiny and widely used). Recommend (a) given the surface is one function with a handful of test cases, no reason to add a dependency for it.
- **Dependency — `ferric init-project`** (an interactive config-creation wizard, named in ADR-014's backlog and the production-readiness plan doc) is explicitly NOT this sprint — v1 only READS an existing, hand-authored `.ferric/config.toml`/user config file (matching how `CLAUDE.md` itself requires no wizard, just creating the file). The wizard remains backlog.
- **Dependency — scope boundary on WHICH fields get config-defaulted.** Covering every CLI flag across every subcommand in one sprint would be a large, sprawling change. Recommend scoping to the fields the production-readiness plan doc itself named (model, ring width, workspace, backend URL, temperature) plus the natural `ModelProfile` group (`quant`/`family`/`ctx`) and `--stream`, applied to BOTH `ferric query` and `ferric mcp` (sharing one `Config` struct) — explicitly deferring `ferric server`/`ferric bench`/`ferric toolbench`'s own flags to a future increment if this proves valuable.

## 5. Recommended Approach
**Primary:** A new `crates/ferric-cli/src/config.rs` module: a `Config` struct (serde `Deserialize`, all fields `Option<T>`) covering exactly the bounded field set from Risks above — `backend`, `model_dir`, `model_file`, `model`, `api_base`, `api_key`, `params_b`, `quant`, `family`, `ctx`, `temperature`, `max_ring`, `profile_dir`, `stream`. A `load_layered(workspace: &Path) -> Config` function reads `<workspace>/.ferric/config.toml` (project) and a hand-rolled cross-platform user-config path (`~/.config/ferric/config.toml` on Linux/macOS, `%APPDATA%\ferric\config.toml` on Windows), merging field-by-field with **project winning over user, user winning over absent** (missing file at either layer is a silent no-op, matching `read_profile`'s established "missing file = no-op" precedent from ADR-029). Each of `QueryArgs`'/`McpArgs`' currently-hardcoded-default fields (`params_b`, `quant`, `family`, `ctx`, `temperature`, `profile_dir`) loses its clap default and becomes `Option<T>`; the final value is resolved as `cli_arg.or(config.field).unwrap_or(today's_hardcoded_default)` — preserving today's exact defaults when neither a flag nor a config file is present (a pure regression-testable claim). `BackendOpts`' already-`Option<T>` fields get the same `.or(config.field)` treatment with no type change at all.

For `Animus.md`: a small, separate function (e.g. in `ferric-prompt` or directly in `query.rs`/`mcp.rs`'s shared config-building path) reads `<workspace>/Animus.md` if present (plain `std::fs::read_to_string`, no parsing, no versioning — deliberately NOT an oovra element) and appends it as a distinct, clearly-delimited block to whichever system prompt text `ferric-prompt` composed (or the `DEFAULT_SYSTEM_PROMPT` fallback) — e.g. `"{composed_or_default}\n\n--- Project instructions (Animus.md) ---\n{animus_md_content}"`. Missing file is a silent no-op (same convention as the config file). Traced as a `Note` (or a small dedicated event) so its presence/absence is auditable in the JSONL trace, matching the project's "never silent" tracing discipline.

**Alternative considered:** folding `Animus.md` into oovra as a new element type. Rejected: oovra elements are versioned, pinned, and composed via a fixed recipe matrix (`recipe_for`) — `Animus.md` is exactly the opposite shape (unversioned, user-edited freeform prose, no recipe slot). Forcing it into that system would need oovra API changes for a feature oovra isn't designed for, when simple string concatenation at the injection point (`system_prompt: Option<&str>`) already does the job with zero new machinery.

**Rationale:** Reusing `resolve_base`'s already-proven precedence-chain idiom (`explicit.or(other).unwrap_or_else(default)`) keeps the config-layering mechanism consistent with code the project already has and has already tested, rather than inventing a new merge convention. Scoping the `Config` struct to a named, bounded field list (not a generic key-value map) makes the ADR-005 boundary ("config never touches security policy") a structural fact, not a review-time hope. Treating `Animus.md` as trusted, harness-level context (not routed through Ornstein's quarantine) matches its actual trust tier — a file the workspace owner wrote themselves, no different from the codebase they're already having the agent operate on.
